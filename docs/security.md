# Security and privacy architecture

**Status:** Phase 1 includes Supabase SSR auth wiring, foundational PostgreSQL RLS policies, and role-scoped company/project permissions, tested with PGlite and synthetic users. This hardening pass preserves the existing Phase 1 candidate and aligns its migration, server actions, UI, tests, and documentation. The system has not been live-Supabase tested, penetration-tested, or security-certified; later-phase controls remain design only.

## 1. Security objectives

1. A user can read or change only data in workspaces where they have an active authorized membership.
2. Recordings and transcripts are private by default; no public object bucket or permanent public URL.
3. A compromised browser/desktop bundle cannot reveal server API keys or gain database-wide access.
4. Processing output and AI answers remain source-attributable and cannot be used as a cross-workspace data channel.
5. Capture survives connectivity loss without erasing local evidence; deletion and retention apply to originals and derived data.
6. Sensitive content is not unnecessarily copied to logs, analytics, test fixtures, or external integrations.

### Implemented Phase 1 controls

- Authenticated web requests use Supabase SSR with the public anon key; no service-role key is used by the web application. The Next.js proxy refreshes the auth session, while protected pages/actions independently call `auth.getUser()`.
- Signup confirmation and callback redirects use one validated canonical `APP_URL`, never an incoming Host, forwarded-host, or request-origin value. Only development permits the localhost fallback/loopback HTTP; other environments require an explicit HTTPS origin.
- The Phase 1 migration enables RLS on profiles, workspaces, membership, companies, projects, meeting types, meetings, and audit logs. Workspace creation is an atomic, narrowly granted `SECURITY DEFINER` function. Active `owner`/`admin` members may create/update companies and projects; active `member` rows are read-only for those entities. All active roles may create meeting drafts, but no role may change meeting lifecycle or membership rows through client SQL. Role invitations/changes and deletes are not implemented.
- Composite foreign keys enforce workspace identity for company, project, meeting type, and meeting references. PGlite tests apply the actual migration and exercise owner/admin/member permissions, cross-workspace reads, forged workspace IDs, joined reads, mismatched project/company, draft-only meeting state, Phase 1 schema boundaries, and hidden audit rows.
- Successful workspace/member/company/project/meeting writes are recorded with minimal metadata; authenticated users have no direct audit-table read/write grants. Table access is revoked first and re-granted narrowly (column-limited insert/update grants only), and the trigger-only functions `set_updated_at`, `validate_meeting_project_company`, and `write_workspace_audit_log` are revoked from `public`/`anon` and granted to `authenticated` solely because table writes execute them. `handle_new_user()` keeps its default grant because the Supabase Auth admin role must execute it from the `auth.users` insert trigger.

These controls have **not** been tested through a live Supabase Auth/PostgREST project. PGlite tests model `auth.uid()` with a test function and do not validate Supabase gateway/session configuration.

## 3. Threat model

| Threat                                                         | Impact                                              | Required mitigations / residual risk                                                                                                                                                     |
| -------------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cross-workspace IDOR or forged workspace ID                    | Meeting/audio disclosure or modification            | Resolve workspace from authorized membership, not client claims alone; RLS and composite FKs; apply tenant filter to every child/vector/object query; two-workspace adversarial tests    |
| Public/leaked recording URL or object key                      | Sensitive audio disclosure                          | Private bucket; short-lived signed URLs; no URL persistence/logging; server authorization before issuance; revoke/expire and audit                                                       |
| Leaked Supabase service role, DB URL, R2/OpenAI/STT key        | Broad data compromise and cost abuse                | Secret manager/env injection; server-only; least-privilege DB/runtime roles; rotate/revoke; separate dev/prod; never commit `.env`; avoid service-role in ordinary user request paths    |
| Malicious/compromised account or stolen session                | Legitimate-session data access                      | MFA/strong auth policy when selected, secure HttpOnly/SameSite cookies, session revocation, role separation, rate limiting, audit log; account takeover remains a residual risk          |
| Forged/replayed chunk registration or checksum mismatch        | Corrupt/mixed recording, duplicate work             | Authenticated session ownership, per-chunk immutable IDs, idempotency key plus checksum, object verification, server-side finalize checks, conflict rejection                            |
| Compromised or poisoned worker/job payload                     | Cross-tenant reads, data corruption, repeated spend | Worker-only credentials; validate job/meeting/workspace relations; typed payloads; restricted DB grants; retry limits, leases, output validation and audit events                        |
| Prompt injection in transcript or malicious participant speech | Manipulated extraction, leakage, tool use           | Treat transcript as untrusted quoted data; no model tools/secrets; strict output schema; validate evidence and tenant IDs; model output cannot authorize operations                      |
| False or overconfident business conclusion                     | Wrong owner/decision/fact used operationally        | Evidence links mandatory; decision status semantics; null unknown owners/deadlines; confidence caveat; user review/correction path; evaluation sets before launch                        |
| Lost/stolen/unlocked device                                    | Local audio disclosure                              | Restrictive file permissions and OS disk encryption; Keychain-backed per-device chunk encryption is a production gate; recording still accessible to malware in an unlocked user session |
| Deletion leaves object/vector/backup remnants                  | Retention/privacy failure                           | Tombstone then durable purge of DB, objects and embeddings; retry/reconcile; explicit backup expiry and legal-retention policy; report limits on immediate backup erasure                |
| Denial of service or provider cost abuse                       | Availability/cost                                   | Per-user/workspace rate and size limits, upload quotas, bounded retries/concurrency, request timeouts, circuit breakers and budget monitoring                                            |
| Analytics/support leak                                         | Secondary disclosure                                | Allowlisted event schema and redaction tests; no raw text/audio/keys/URLs by default; access-controlled audit/support tools                                                              |

## 4. Identity, authorization, and tenant isolation

- Supabase Auth provides user identity. `profiles.id` maps to `auth.users.id`; active `workspace_members` rows and roles authorize workspace operations.
- Phase 1 role contract: `owner` and `admin` can create/update companies and projects; `member` can read them but cannot create/update them. All active roles can read workspace data and create meeting drafts. No role can delete these rows, change meeting lifecycle, or manage memberships in Phase 1. A signed-in user creating a workspace becomes its first active owner. Server actions and UI mirror this policy; RLS is authoritative.
- Every user-facing route authenticates the caller, loads the target resource using a workspace-scoped repository, checks role/operation, and relies on RLS as a second enforcement layer. Never trust a `workspace_id` merely because it came from a hidden form field, JWT custom claim, URL, desktop client, or AI response.
- Enable RLS on every tenant table that is reachable by a user-scoped key. Policies use active membership, with role-limited writes. Test reads, inserts, updates, deletes, nested joins, storage signing and vector lookup using two unrelated workspaces.
- Avoid recursive `workspace_members` policy logic. Prefer an audited server membership-management operation or a narrowly scoped `SECURITY DEFINER` helper with fixed `search_path`, constrained grants, and no caller-selected identity. Revoke default public execute as appropriate.
- **Browser:** may hold only the public Supabase URL/anon key and the authenticated user's session/JWT. User-scoped data access is RLS-protected; no service-role, database URL, object-store secret, or provider key may enter a client bundle.
- **Desktop:** the Tauri frontend never connects directly to PostgreSQL/Supabase tables and never receives privileged credentials. It stores/uses only the user's Auth session, sending operations through the versioned authenticated `/api/v1` boundary. Rust capture/upload coordination follows the same user-scoped API rule.
- **Next.js/API:** validates the caller's Supabase Auth identity and performs user-scoped reads/writes with a request-bound Supabase client carrying that user's JWT, so RLS remains active. It derives workspace access from membership and re-checks resource ownership; body/URL workspace IDs are selectors, not authorization. It must not use `SUPABASE_SERVICE_ROLE_KEY` as a convenience client for ordinary user requests.
- **Storage signing:** if an API operation needs to issue a short-lived object URL, first authorize the exact meeting/recording/chunk with the caller's JWT/RLS and record the action. Use a storage-only least-privilege signer/broker scoped to opaque single-object operations; do not grant the API a database-wide service role merely to sign URLs. The API never treats possession of a signed URL as continuing authorization.
- **Worker:** may require privileged database/storage access for queue claims and internal processing, but any Supabase service-role credential exists only in a separately deployed worker secret environment—not browser, desktop, or shared web/runtime env. Prefer dedicated worker DB roles/narrow RPCs and bucket-scoped credentials; give only stage-required access, validate `job → meeting → workspace` on every operation, enforce lease fencing, and append redacted audit/processing events. Keep the worker internal, with no public service-role endpoint. This is a high-impact trust boundary requiring security review before production.
- Use secure, HttpOnly, SameSite cookies for web sessions; apply CSRF/origin checks for state-changing cookie-authenticated routes. Use TLS in transit and short session lifetimes/revocation appropriate to product policy.

## 5. Recording and object security

- Obtain and persist applicable consent acknowledgement before capture; make recording visible throughout. Explain that the user is responsible for informing participants under applicable law/policy.
- Keep microphone and system audio separate and local while recording. Local files remain under the OS app-support directory, with restrictive permissions. Keychain-backed per-device encryption is planned before production; never put the encryption key in `.env`, the manifest, browser storage, or frontend bundle.
- The storage bucket is private. Server-issued signed URLs are short-lived and scoped to one opaque object key and one operation. A signed URL is a bearer capability until expiration; never write it to logs or analytics. Avoid predictable keys as the only authorization control.
- Server validates membership, recording ownership, allowed source/sequence and canonical idempotency identity, then independently verifies the actual stored object's expected key, byte size and checksum. Client upload completion is provisional; only server-set `verification_state=verified` is durable. Database uniqueness prevents retries from creating duplicate canonical chunks, while conflicting bytes are rejected. Finalization requires every declared required source/range to be verified. Use TLS and provider-side server-side encryption; define deletion/lifecycle rules and verify storage behavior. See [database.md](database.md) and [recording.md](recording.md).
- Serve audio only after an authenticated permission check, via a short-lived signed URL or controlled streaming endpoint with restrictive response headers. Do not make transcript/audio accessible from a public CDN by default.

## 6. AI/STT and data handling

- `OPENAI_API_KEY` and `ASSEMBLYAI_API_KEY` are worker/server secrets. Browser and Tauri renderer code receive no provider keys. Model identifiers and provider configuration are environment-controlled; prompts and schemas are centralized/versioned.
- Send only the audio/transcript and scoped context required for the requested operation. Custom terminology must be authorized for that workspace. Before production, review provider DPA, retention/training settings, subprocessors, regions, breach notice and deletion guarantees; do not claim zero retention unless contractually/configurationally verified.
- Transcripts are untrusted content, not executable instructions. Do not enable tool/function access for extraction. Enforce strict schemas and source-ID checks after every model response. Never use model output to authorize workspace access, issue signed URLs, modify integrations, or make external business changes.
- Store minimum raw vendor payloads with explicit access/retention if operationally necessary. Structured logs carry IDs, stage, duration, error category and safe correlation IDs—not spoken text, note contents, authorization headers, signed URLs, raw request bodies or secret values.

## 7. Deletion, audit, and retention

A deletion request first tombstones the meeting and, in the same database transaction, enqueues an idempotent purge/outbox record. That commit immediately blocks ordinary reads, search/vector retrieval, new signed-media URLs, and new worker writes, even while bytes still await physical deletion. The purge covers the complete lineage: meeting → recordings → sources/chunks → original and rendered files → transcription runs/segments/speaker maps → notes/markers/participants/topics → analysis runs/summaries/claims/typed intelligence/evidence → knowledge chunks/embeddings/vectors → provider artifacts/exports/caches/derived files. Tombstoned knowledge is never searchable; retrieval must join/filter against the authoritative non-deleted meeting.

PostgreSQL and object storage cannot commit atomically. Keep a durable per-object deletion ledger (backend/key/version, state, attempts, safe error code) until the store confirms deletion or absence; retry transient failures and reconcile orphaned objects from manifests/prefixes. Failed deletions remain visible as `purge_pending`, alertable, and never silently marked complete. Mark the primary purge complete only after relational/search rows and required objects are confirmed; account for already-issued signed URLs until their short expiry. Audit actor, target, request ID, action and outcome without copying deleted content. The detailed ordered purge contract is authoritative in [database.md](database.md).

Define configurable retention for local recordings, server originals, transcripts and derived records. Document backup expiration and legal holds; distinguish application deletion from backup expiry. Local data is never deleted merely because upload started. Provide user-visible deletion status and final confirmation when primary stores are purged.

Phase 1 currently audits successful workspace creation, initial owner membership, company/project create/update, and meeting draft creation; the audit table is append-only and not client-readable. Extend auditing before later phases to cover membership/role changes, recording start/stop/finalize, signed media access where feasible, meeting export/deletion, processing retries, AI reprocessing, integration linking/unlinking, and privileged worker actions. Define retention and privileged read access before production.

## 8. Environment and operational safeguards

`.env.example` documents names only and labels future-phase variables; a developer's real `.env` is ignored and production secrets belong in the deployment secret manager. `NEXT_PUBLIC_*` variables are public by definition. `APP_URL` is the single server-only canonical origin used by signup confirmation and callback redirects: it is validated by the Next.js instrumentation startup hook, again whenever an authenticated server client is created, and at each redirect, so an unset or non-canonical value fails closed instead of falling back to a request-controlled host. Development may use the loopback default; staging/production require an explicit HTTPS origin. Do not import server-only packages into Next client components or the Tauri renderer. Validate required configuration at server/worker startup and fail closed when a production secret/provider is missing; never silently switch to permissive storage/auth behavior.

Separate development, test and production Supabase projects, buckets, provider keys, telemetry projects and encryption keys. Rate-limit auth-sensitive/upload/AI endpoints, bound file size/duration and worker concurrency, apply provider timeouts, and alert on repeated failures or abnormal spend. Sentry/PostHog integration is optional and privacy-filtered; environment presence alone does not mean telemetry is enabled.

## 9. Phase 1 limitations and production gates

The migration and web auth wiring are implementation artifacts, not evidence of a deployed or production-hardened service. Before accepting sensitive real meetings: apply and verify RLS on a real Supabase project; test email/session/redirect behavior; implement signed-object access, secret scanning, device-key lifecycle, consent UX, deletion reconciliation, provider contractual review, dependency scanning, backup restore, worker privilege review, rate limits, incident response, and a security-focused two-workspace suite. No security certification or legal compliance claim is made.
